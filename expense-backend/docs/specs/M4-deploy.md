# M4 部署與自動化維護 — 規格草案（高風險，須使用者核准）

狀態：草案　風險：高　依賴：M1、M2（上線前必須完成）　雲端供應商**尚未決定**，下列應用層需求與供應商無關

## 目的
讓系統能在公網上長期自我維護：自動更新、自動重啟、自動備份、異常通知，且每項都可驗證。

## 設計（需求層，供應商待定）
- **容器：** `Dockerfile`（非 root、唯讀檔案系統、僅資料目錄可寫、固定相依版本）；`docker-compose` 內含應用與 Caddy。
- **HTTPS：** Caddy 自動申請／續期憑證；HTTP 一律轉址 HTTPS；HSTS；安全標頭（CSP、`X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy`）；請求本體上限與 M2 一致。
- **網路：** 防火牆只開 80／443；SSH 只允許金鑰且限定來源 IP；關閉密碼登入。
- **自動更新：** 系統安全更新自動安裝，必要時於凌晨自動重開；Dependabot 發相依更新；CI 跑 `pip-audit`、`bandit`、全部測試。
- **部署：** GitHub Actions：測試全綠才部署；部署後健康檢查失敗自動回復舊版。
- **自動重啟：** 程序崩潰自動拉起。
- **備份：** SQLite 持續複寫到儲存桶（Litestream 或同等）；圖片目錄每日同步；儲存桶啟用版本控制與保留期；**每季還原演練腳本**自動還原到暫存環境並比對筆數與檔案雜湊，輸出報告。
- **監控與通知：** 外部服務每 5 分鐘檢查 `/api/v1/health`，異常通知；磁碟 >80% 通知；費用預算警示；**每月健康報告**（備份次數、封鎖次數、磁碟、異常事件）寄給指定負責人。
- **機密：** 環境變數或雲端機密管理，repo 內不得有金鑰；`.env` 已忽略。

## 驗收條件
1. 本機以 compose 啟動後：`curl http://` 被 301/308 轉到 HTTPS（測試環境用本機憑證）；回應含 HSTS 與 CSP。
2. 殺掉應用程序 → 30 秒內自動恢復且 `/health` 回 200。
3. 超過本體上限的請求在代理層被拒（413），不進到應用。
4. CI：任一測試失敗或 `pip-audit` 發現高危漏洞 → 不部署。
5. 部署一個故意壞掉的版本 → 健康檢查失敗後自動回到上一版（在測試環境演練）。
6. 備份：寫入 N 筆資料後刪除本機資料庫，從備份還原，筆數與圖片雜湊完全一致（腳本化並有報告）。
7. 容器以非 root 執行；資料目錄以外唯讀（以 `docker inspect`／寫入嘗試驗證）。
8. repo 以祕密掃描工具檢查無金鑰。
9. 每月健康報告可由腳本產生並寄出（測試環境用假寄信）。

## 規格挑戰
- 自動重開機與自動更新可能在你操作時中斷服務 → 限定凌晨維護時間窗。
- 備份本身含個資 → 儲存桶需加密、限權、限制公開存取；還原演練只能在受控環境。
- 6 人規模是否需要自動回復舊版這套機制？成本與價值需權衡（可降級為「手動一鍵回復」）。
- 跨境：區域若在境外，需法遵確認並於隱私說明載明。
