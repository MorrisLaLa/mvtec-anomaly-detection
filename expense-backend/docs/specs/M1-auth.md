# M1 身分與授權 — 規格草案（高風險，須使用者核准）

狀態：草案　風險：高　依賴：無　會改動資料庫 schema（新增 `devices` 表、`expenses.device_id`）→ **核准即視為同意此 schema 變動**

## 目的
公網上只有已登記的手機能呼叫 API；每支手機有角色；申報人身分由後端決定，不信任用戶端欄位。

## 設計
- **裝置金鑰：** `secrets.token_urlsafe(32)`；只在建立時顯示一次；資料庫只存 SHA-256 雜湊；比對用 `hmac.compare_digest`。
- **角色：** `submitter`（申報人）、`reviewer`（主管審核）、`admin`（管理）。
- **管理方式：** 只提供命令列 `python -m app.admin`（建立／列出／撤銷／輪替裝置），**不提供 HTTP 管理端點**，縮小攻擊面。
- **請求驗證：** `Authorization: Bearer <金鑰>`。除 `GET /api/v1/health`（只回 `{"status":"ok"}`）與靜態頁 `/pwa/*` 外，所有 `/api/v1/*` 都必須驗證。
- **授權表：**

| 端點 | submitter | reviewer | admin |
|---|---|---|---|
| POST /submit | ✓ | ✓ | ✓ |
| GET /rules | ✓ | ✓ | ✓ |
| POST /corrections | ✓ | ✓ | ✓ |
| GET /pending-rule-suggestions、POST …/confirm | ✗ | ✓ | ✓ |
| GET /export | ✗ | ✓ | ✓ |

- **身分來源：** `employee` 一律取自裝置登記的名稱，忽略表單欄位。
- **冪等：** `(device_id, client_id)` 唯一；同一 `client_id` 內容不同 → 409。
- **限流：** 每個 IP 15 分鐘內驗證失敗 10 次 → 封鎖 15 分鐘（回 429）；每個裝置每分鐘最多 60 次請求。
- **金鑰期限：** 預設 180 天到期；撤銷後下一次請求即失效。
- **一致性：** 驗證失敗一律回相同的 401 本體，不洩漏「金鑰不存在」與「已撤銷」的差別；金鑰與雜湊不得寫入任何記錄。

## 驗收條件（每條都要有自動化測試）
1. 無標頭、錯誤金鑰、已撤銷金鑰、已過期金鑰呼叫 `/submit` → 全部 401，回應本體相同。
2. submitter 呼叫 `/export`、`/pending-rule-suggestions`、`…/confirm` → 403；reviewer 可以。
3. 申報人在表單偽造 `employee` → 資料庫寫入的是裝置名稱。
4. 同一 IP 連續 10 次錯誤金鑰後，第 11 次（即使金鑰正確）→ 429，15 分鐘後恢復（測試用可調的時間）。
5. 單一裝置 1 分鐘內第 61 次請求 → 429。
6. 同一 `client_id` 相同內容重送 → 200 `duplicate=true`；內容不同 → 409；他人裝置使用相同 `client_id` → 建立新紀錄，不洩漏前者。
7. 撤銷裝置後，該金鑰的下一個請求 → 401。
8. 資料庫與測試記錄中搜不到明文金鑰。
9. `GET /health` 不需要金鑰，且回應不含版本、主機等資訊。
10. 建立裝置的命令列：金鑰只在建立時輸出一次；`list` 只顯示名稱、角色、狀態、到期日。

## 規格挑戰（對抗／法遵，由我先自審，待你與日後獨立審查補強）
- 金鑰被偷（手機遺失、XSS）：可用撤銷與到期降低，無法根絕；因此 M2 要求前台輸出全面轉義，M4 要求 CSP。
- 暴力猜測：金鑰 256 位元不可猜，限流主要用來擋流量與探測。
- 以 IP 封鎖可能誤傷同一出口 IP 的合法同事（公司網路）：封鎖鍵改為「IP + 嘗試使用的金鑰前綴雜湊」？→ **待決定**（見下）。
- 資料蒐集最小化：裝置表只存名稱、角色、時間，不存手機型號或位置。

## 待使用者決定

- Q3：金鑰預設 180 天到期是否合適？

## 修訂 1（依使用者回覆）
- **Q2（401／429 與「4xx 不重試」規則）：** 使用者不同意把 429 視為自動重試。**採用方案 B（建議）**：維持「所有 4xx 都不進自動重試佇列」，但增加**使用者主動觸發**的處理，不違反原規則：
  - 401（金鑰失效／過期／撤銷）：列表顯示「裝置未授權，請重新綁定」；使用者重新綁定成功後，**由使用者按「重送失敗項目」**才會重新送出（不是自動）。
  - 429（限流）：顯示「請稍後再送（約 N 分鐘）」，N 取自伺服器的 `Retry-After`；使用者稍後按「重送」。
  - 其他 4xx（422 資料錯）：顯示錯誤訊息，使用者修正內容後再送。
  - `failed` 清單保留收據圖與簽名，不會遺失；前台新增「重送／刪除」按鈕（目前沒有，見稽核 A16）。
  - 伺服器端同時讓 429 很少發生：限額遠高於 6 人正常用量；封鎖鍵改為「IP + 金鑰雜湊」，降低同一公司出口 IP 誤傷同事的機會。
- 驗收條件新增：
  11. 401 的項目不自動重送；重新綁定後按「重送」才送出且成功入庫。
  12. 429 回應含 `Retry-After`；前台顯示等待時間；不自動重送。
  13. 失敗項目可刪除；刪除前有確認。

### 使用者確認（修訂 2）
- Q2：**方案 B 已確認**（4xx 一律不自動重試；401／429 由使用者手動重送；失敗項目可刪除）。

## 修訂 3（使用者回覆 Q3，台北 2026-10-13）
- **Q3：金鑰到期時間要能由 admin 自行設定，目前暫定 1 年（365 天）。** 取代「固定 180 天」：
  - 設定檔 `device_key_default_days: 365`（預設值）。
  - 建立裝置時可指定：`python -m app.admin create-device --name … --role … [--days N | --expires 日期]`；未指定用預設。
  - 事後可調整：`python -m app.admin set-expiry <裝置> (--days N | --expires 日期 | --never)`；`--never` 需明確加旗標且在 list 顯示「永不過期」警示。調整立即生效。
  - `list` 顯示每支裝置的到期日與剩餘天數；到期前 30 天在前台提示重新綁定。
- 驗收條件新增：
  14. 不指定天數建立裝置 → 到期日 = 建立時間 + 365 天（以可調時鐘測試）。
  15. `--days 30` → 30 天後失效；`set-expiry --days 400` 後原本 365 天到期的金鑰在第 366 天仍有效。
  16. `set-expiry` 縮短到已過去的日期 → 該金鑰下一個請求即 401。
  17. 到期前 30 天內，`/api/v1/health` 之外的回應帶 `X-Key-Expires-In-Days` 標頭，供前台提示（不含金鑰任何資訊）。
- 原驗收條件中「180 天」一律以此為準。

## 修訂 4（實作時的設計決定，台北 2026-10-13；請使用者知悉）
1. **限流封鎖只針對「無效金鑰」，有效金鑰不受影響**（偏離原驗收條件 4「即使金鑰正確也回 429」）。理由：原先「IP＋金鑰雜湊」的封鎖鍵會讓攻擊者每次換一把金鑰就繞過封鎖；改成只依 IP 計失敗次數、但有效金鑰照常通過，既擋掉探測流量，也不會誤傷同一出口 IP 的合法同事（金鑰 256 位元，猜中不可行）。測試已改寫為此行為。
2. **同名且未撤銷的裝置不可重複建立**（避免 `revoke`／`set-expiry` 以名稱操作時有歧義）；撤銷後可重用名稱。
3. **冪等的內容比對**使用 `payload_hash`（新增 `expenses.payload_hash` 欄位，屬 M1 驗收條件 6 所必需的 schema 變動）；相同裝置＋相同 `client_id` 同時抵達的請求，唯一鍵衝突時回傳既有結果而非 500。
4. **檔案以裝置命名空間存放**（`<storage>/d<裝置ID>/<client_id>/…`）：先前以 `client_id` 為目錄，兩支裝置使用相同 `client_id` 時後者會覆寫前者的收據，已由測試重現並修正。
5. **IP 取自 `request.client.host`**。放在反向代理（Caddy）之後時會是代理的 IP，需在 M4 設定受信任代理並改讀 `X-Forwarded-For`；在那之前不得直接上公網。
6. 驗證只接受 `Authorization: Bearer <金鑰>`（scheme 區分大小寫）；金鑰放在網址參數不被接受（已測）。
7. 限流狀態存在單一程序的記憶體中；重啟即清空、不跨多個程序。對單機 6 人規模可接受，擴充時需改外部儲存。
8. 前台：`sync.js` 現在從 `localStorage['expense_device_key']` 讀金鑰並帶上標頭；**綁定畫面尚未做（F1／視窗 4）**，目前只能手動寫入該金鑰，所以現有前台在沒有金鑰時會收到 401。

## 修訂 5（使用者要求：現場人員第一次設定不要打字；連結與 QR 並行）— 需使用者再次核准
**狀態：草案，未實作。** M1 已核准；此修訂新增資料表與一個無需驗證的端點，屬安全相關設計，必須先經使用者核准。

### 設計：一次性配對碼（取代「把長金鑰傳給現場人員」）
- 管理員 `python -m app.admin create-device …` 除了建立裝置，同時產生**一次性配對碼**：隨機 128 位元（`pt_…`），資料庫只存雜湊；**24 小時內有效、只能用一次**（有效時間可設定）。
- 指令輸出：
  1. **配對連結**：`https://<主機>/pwa/expense-demo.html#pair=<配對碼>`（放在網址的 `#` 之後，不會被送到伺服器或寫進存取記錄）。
  2. **QR 圖檔**：內容就是上面的連結，輸出成 PNG；管理員可貼在螢幕上或傳給對方掃。
  3. 長金鑰不再顯示（保留 `--show-key` 供手動輸入備案）。
- 新端點 `POST /api/v1/pair`（無需金鑰）：body `{token}` → 成功回 `{key, name, role, expires_in_days}`，並把配對碼標記為已使用；**無效、過期、已用一律回相同的 400**，不洩漏差別；對同一 IP 嚴格限流（沿用驗證失敗的計數與封鎖）。
- 前台讀取 `#pair=…` → 呼叫 `/pair` → 儲存金鑰 → 立刻用 `history.replaceState` 清掉網址中的配對碼 → 進首頁。
- 新資料表 `pairing_codes(id, device_id, token_hash UNIQUE, created_at, expires_at, used_at)`。

### 驗收條件
1. 配對碼只能用一次；第二次回 400（本體與「無效碼」相同）。
2. 過期（以可調時鐘）→ 400。
3. 資料庫與記錄中找不到明文配對碼或金鑰；配對碼雜湊與金鑰雜湊分開。
4. 配對成功回傳的金鑰可正常呼叫其他端點；配對碼本身**不能**當金鑰使用。
5. `/pair` 受 IP 失敗限流保護（連續失敗 10 次後回 429）。
6. 管理員撤銷裝置後，尚未使用的配對碼同時失效。
7. QR 圖檔掃描後內容等於配對連結（以 pyzbar 解碼驗證）。
8. 前台：開啟含 `#pair=` 的網址 → 自動配對，網址列的配對碼被清除；失敗時顯示可行動的訊息。

### 風險與取捨（請知悉）
- **連結／QR 在被使用前等同金鑰**：任何拿到它並先使用的人就能綁定。降低風險的方法：24 小時有效、一次性、請用私訊單獨傳給本人、當面掃 QR 最安全。
- 若現場人員把連結轉貼到群組，群組內任何人都可能先用掉；因此建議**一人一碼**（本設計即為一人一碼）。
- 手機被掃了別人的 QR 並綁定成功時，管理員可在 `list` 看到「已綁定時間」，並可撤銷。

## 修訂 6：管理員在手機上解除登入封鎖（使用者核准，台北 2026-10-24）
- 起因：走 Tailscale Funnel 時，伺服器可能看不出每支手機的來源，所有人共用同一個失敗計數；有人打錯 10 次，其他人 15 分鐘內無法綁定新手機（資安審查 D2）。
- 使用者要求：「手機上就可以放行」。這項修訂取代本規格「不提供任何 HTTP 管理端點」的原則，**例外只有這一個端點**。
- `POST /api/v1/admin/unblock`：只限 `admin` 角色（其他角色 403，未授權 401）；清除全部失敗計數；回傳 `{"ok": true, "cleared": <被解除的來源數>}`；在存取記錄中寫入 `unblock` 事件（含裝置 id）。有效金鑰本來就不受封鎖影響，所以管理員一定呼叫得到。
- 前台：設定頁的「解除登入封鎖」按鈕，只在角色為 admin 時顯示；隱藏按鈕不是安全措施，權限由伺服器檢查。
- 限制：失敗計數存在單一程序的記憶體中（目前 uvicorn 只有一個 worker）；如果攻擊還在持續，解除後會立刻再次被封鎖，根本解法仍是 D2 的實機確認。
- 驗收：`tests/test_admin_unblock.py`、`tests/test_admin_unblock_ui.py`。
