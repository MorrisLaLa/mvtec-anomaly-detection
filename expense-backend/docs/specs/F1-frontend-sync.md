# F1 前台同步與裝置綁定 — 規格草案（中風險，監督放行即可；含使用者已確認的決定）

狀態：草案　風險：中　依賴：M1（綁定與 401）　範圍：`frontend/expense-demo.html`、`frontend/sync.js`
對應工作視窗：WINDOWS 第 4 項

## 已確認的決定
- **方案 B（Q2）：** 所有 4xx 不自動重試；失敗項目留在本機，由使用者按「重送／刪除」。401 重新綁定後由使用者按「重送失敗項目」。429 顯示「請約 N 分鐘後再送」（`Retry-After`）。
- **Q4（使用者新需求）：手機連上 Wi‑Fi 才自動上傳，不消耗手機行動網路用量。**

## 設計

### 1. 裝置綁定（依 M1）
- 首次開啟（或 401 後）顯示綁定畫面，輸入管理員給的金鑰；金鑰存本機，之後每次請求帶 `Authorization: Bearer`。
- 到期前 30 天（`X-Key-Expires-In-Days`）顯示提醒。

### 2. 僅 Wi‑Fi 上傳（預設開啟，可在設定關閉）
- 申報一律先存本機佇列（既有行為）。是否「立即送出」由上傳策略決定：
  - 策略 `wifi_only`（預設）：只有確認連線類型為 Wi‑Fi／乙太網路時才自動上傳。
  - 策略 `any`：不限網路（使用者自行切換）。
- **偵測能力（誠實說明，需實機驗證）：**
  - 瀏覽器的 `navigator.connection.type`（Network Information API）可區分 `wifi`／`cellular`。我印象中這個 API 在 Android 的 Chrome 有支援，**在 iPhone 的 Safari 沒有支援**，所以 iPhone 無法自動判斷連線類型。尚未在實機驗證。
  - **Android（API 可用）：** `wifi`／`ethernet` → 自動上傳；`cellular`／`unknown`／`none` → 保守處理，不上傳，標示「等待 Wi‑Fi」。連線類型改變（`change` 事件）時自動重新檢查並上傳。
  - **iPhone（API 不可用）：** 無法自動判斷 → 改為「手動上傳」模式：項目標示「待上傳（請在 Wi‑Fi 下按『立即上傳』）」，使用者確認自己在 Wi‑Fi 後按下才送出。畫面明確說明原因。
  - 每筆項目有「本筆改用行動網路上傳」的明確按鈕（使用者主動選擇才會用行動網路）。
- **「等待 Wi‑Fi」不是失敗：** 不套用 4xx／重試規則，不計入遞增重試；只在網路條件符合或使用者手動觸發時才送。
- **限制（重要）：** PWA 在頁面關閉時**無法可靠地在背景上傳**（iPhone 沒有背景同步；Android 的背景同步支援有限且不保證）。因此「連上 Wi‑Fi 就自動上傳」只在 App（網頁）開著時成立。**若需要真正的背景自動上傳（只在 Wi‑Fi、App 關閉也上傳），要包成原生 App**（Android 可設定「僅不計量網路」；iOS 可禁止蜂巢網路傳輸）——這正是先前列出「值得做原生 App」的條件之一，目前先不做。

### 3. 降低用量（即使使用者選用行動網路也很省）
- 上傳前在手機端壓縮圖片：長邊 ≤ 1600 px、JPEG 品質約 0.8（預估每張約 200–400 KB，原本約 2 MB）。
- 簽名、憑證圖同樣壓縮；文字欄位本身僅數 KB。
- 估算：每月 50 筆、每筆約 0.5 MB → 約 25 MB／月（僅在使用者選擇用行動網路時才會發生）。

## 驗收條件
1. 模擬 `navigator.connection.type = 'cellular'`：申報後**沒有任何請求送出**，項目標示「等待 Wi‑Fi」，佇列保留。
2. 將類型改成 `wifi` 並觸發 `change`：項目自動上傳成功，佇列清空。
3. API 不可用（iPhone 情境）：不自動送出；按「立即上傳」才送出；畫面有說明文字。
4. 「本筆改用行動網路上傳」按鈕：僅該筆立即送出，其他筆仍等待。
5. 設定切到 `any`：任何網路皆自動上傳。
6. 上傳的圖片長邊 ≤ 1600 px、檔案 ≤ 600 KB（以合成大圖測試）；後端仍能解析壓縮後圖片中的 QR（合成 QR 測試）。
7. 「等待 Wi‑Fi」的項目不出現在失敗清單，不觸發遞增重試計時器。
8. 方案 B 全部驗收（4xx 不重試；401 重新綁定後手動重送成功；429 顯示等待時間；失敗項目可重送／刪除，刪除前確認）。
9. 既有前台測試仍全綠。
