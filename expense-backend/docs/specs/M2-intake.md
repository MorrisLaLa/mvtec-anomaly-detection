# M2 收件與儲存加固 — 規格草案（高風險，須使用者核准）

狀態：草案　風險：高　依賴：M1　不改既有欄位；新增記錄檔與（可選）每日計數表 → 若用資料表則為 schema 變動，核准即同意

## 目的
讓 `/submit` 在公網上能抵擋惡意或誤用的輸入，並蒐集最少的個資。

## 設計
- **圖片驗證：** 以魔術位元組判斷僅允許 PNG／JPEG／WebP；用 Pillow `verify()` 驗證；像素上限 24MP（超過 → 422，不解碼）；`parse_invoice_qr` 同樣套用像素上限。
- **重新編碼：** 存檔前一律重新編碼並**移除 EXIF（含 GPS）**；副檔名依實際格式。
- **大小限制：** 單檔 ≤ 5 MB、整個請求 ≤ 15 MB（應用層在讀取本體前以 `Content-Length` 與串流計數雙重限制；反向代理同樣設定，見 M4）。
- **欄位限制：** store ≤ 100、note ≤ 500、category ≤ 30、owner_case_no ≤ 50、doc_type ∈ {統一發票, 收據, 無單據}；移除控制字元。
- **每日上限：** 每裝置每日最多 100 筆申報、每日上傳總量上限 200 MB；超過 → 429。
- **檔案不對外：** 收據、簽名、憑證只能透過 M3 的授權端點讀取；不得有任何靜態路徑指向資料目錄。
- **存取記錄：** 結構化 JSON 記錄（時間、裝置 ID、路由、狀態碼、位元組數、耗時），**不記錄請求本體與任何金鑰**；保留 90 天，自動輪替。
- **前台轉義：** `expense-demo.html` 所有來自使用者資料的輸出一律轉義（修 A9）。
- **保存期限：** 設定檔 `retention_days`（預設待定）；法定保存年限須由使用者與會計／法務確認，本規格不自行決定。

## 驗收條件
1. 偽造副檔名的非圖片（文字、HTML、可執行檔）上傳 → 422，且資料目錄無新檔。
2. 25MP 以上圖片 → 422，且處理過程記憶體不超過設定上限（測試以小上限模擬）。
3. 含 GPS EXIF 的 JPEG 上傳後，儲存的檔案 EXIF 為空（以 Pillow 讀回驗證）。
4. 單檔 5MB+1 → 413；整個請求 15MB+1 → 413，且伺服器未讀完整個本體（以串流計數驗證）。
5. 各欄位超長 → 422；欄位含控制字元 → 被移除或 422（擇一，測試固定行為）。
6. 同一裝置第 101 筆（當日）→ 429；隔日（測試用可調時鐘）恢復。
7. 存取記錄存在、格式為 JSON、不含 Authorization 值與請求本體；90 天以上的記錄被輪替刪除。
8. 以 Playwright 注入含 `<img onerror=...>` 的店名，頁面不執行腳本（`alert`／全域旗標未被觸發）。
9. 嘗試以 `/data/...`、`/receipts/...`、`../` 等路徑取得檔案 → 404／無檔案內容。
10. 既有 79 個測試仍全數通過（不得為了通過而改測試，若測試本身與新規格衝突須書面說明）。

## 規格挑戰
- 重新編碼可能降低辨識 QR 的成功率 → 驗收：重新編碼後的圖片 QR 仍可解析（合成測試）。
- 移除 EXIF 後，無法用來證明拍攝時間／地點 → 這是蒐集最小化的取捨，請使用者確認會計上是否需要。
- 簽名圖屬個資；存放期限與刪除機制須與保存年限一併決定。
- 若雲端區域在台灣以外（例如東京），圖片屬跨境傳輸 → 法遵需確認並於隱私說明載明。
