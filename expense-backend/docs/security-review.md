## 四、確認攻擊已被擋住（測試為綠）

- **授權**：逐一列舉所有已註冊的 API 路由（日後新增的也算）→ 匿名一律 401；申報人呼叫主管端點（匯出、審核、讀檔、規則確認）→ 403；畸形、超長、非 ASCII 或含 SQL 的 Authorization → 401，不會 500；金鑰放在網址或 Cookie 不被接受；`/pair` 收到各種怪型別一律回同一個 400。
- **時序**：金鑰與配對碼都是先算雜湊再查詢，攻擊者無法從回應時間逐字元猜出秘密（程式推論，未量測）。
- **注入**：SQL 片段寫進欄位或匯出篩選都不會生效；CSV 開頭為 `= + - @` 的值會被中和。
- **上傳**：SVG、HTML、GIF、PDF、執行檔、只有 PNG 檔頭的檔案偽裝成 PNG → 422，磁碟不留檔；`../../etc/passwd` 這類檔名無效（伺服器不使用上傳檔名）；PNG 後面夾帶腳本的多型檔與 PNG 文字區塊，重新編碼後都會消失；9 億像素的檔案炸彈在幾秒內回 422；檔案端點的路徑穿越或資料庫中指向儲存區外的路徑 → 404；`/pwa` 靜態目錄讀不到原始碼與設定。
- **前台**：主管審核畫面中店名、案號、類別的儲存型 XSS 不會執行；配對碼開啟後不會留在網址列、`localStorage` 或 DOM。
- **部署**：`rollback.sh` 擋下 13 種命令注入與選項注入的版本參數；compose 沒有 privileged、host network、docker.sock 或 cap_add，app、ops、litestream 都是唯讀、`cap_drop: ALL`、`no-new-privileges`，且沒有對外連接埠；Funnel 版 Caddy 只綁 127.0.0.1；Dockerfile 以非 root 執行，沒有 `curl | sh`；SSH 防火牆的來源範圍必須由使用者指定；部署檔與設定檔中找不到金鑰樣式的字串。
- **重放**（既有測試已涵蓋）：同一裝置、同一 client_id 但內容不同 → 409；配對碼只能用一次，並發時以原子更新保證只有一個成功。

## 五、低風險，記錄即可（未修）

- 每日上限與重複發票檢查都是「先查再寫」：同時送出的請求可能各超出一點，或同一張發票同時從兩台裝置送出時兩筆都被核准。影響範圍受每分鐘 60 次的限流約束（未實測）。
- 匯出的 `from`／`to` 沒有驗證日期格式（只會篩錯，不會造成注入）。
- 配對連結在前台清掉網址之前，瀏覽器可能已記下完整網址（歷史紀錄或同步）。配對碼只能用一次、24 小時過期，可以降低這個風險，但無法完全消除。
- 有 QR 的申報沒有檢查「支出日期在未來」（只檢查發票日期）。
- 裝置金鑰以明文存在 `localStorage`（網頁應用必然如此，一旦有 XSS 就能被讀走，所以 D3 很重要）；PIN 也是明文，但它只是方便功能，不是安全邊界（稽核 A14）。
- 管理員可以審核自己的申報（設計如此，事件中會標記 `self_review`）。
